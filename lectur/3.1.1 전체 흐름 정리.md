### *새로운 할인 정책 개발*
- 다형성 덕분에 새로운 정률 할인 정책 코드를 추가로 개발하는 것 자체는 아무 문제가 없음


### *새로운 할인 정책 적용과 문제점*
- 새로 개발한 정률 할인 정책을 적용하기 위해서는 *클라이언트 코드인 주문 서비스 구현체*도 함께 변경해야함.
- 인터페이스와 구체 클래스 모두 함께 의존 -> **DIP 위반**


### AppConfig를 사용하여 관심사를 분리
- AppConfig는 애플리케이션의 전체 동작 방식을 구성(config)하기 위해, 구현 객체를 생성하고, 연결하는 책임 
- 이제부터 클라이언트 객체는 자신의 역할을 실행하는 것만 집중, 권한이 줄어듬(책임이 명확해짐)

### AppConfig 리팩터링 
- 구성 정보에서 역할과 구현을 명확하게 분리 
- 역할이 잘 드러남 
- 중복 제거

## 새로운 구조와 할인 정책 적용

- 정액 할인 정책 정률% 할인 정책으로 변경 
- **AppConfig**의 등장으로 애플리케이션이 크게 *사용 영역*과, 객체를 생성하고 *구성(Configuration)하는 영역*으 로 분리 
- 할인 정책을 변경해도 AppConfig가 있는 구성 영역만 변경하면 됨, 사용 영역은 변경할 필요가 없음. 물론 클라 이언트 코드인 주문 서비스 코드도 변경하지 않음
